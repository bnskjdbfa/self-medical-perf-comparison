# 오늘의 마지막 성능 후보 — 필수동의 진행 상태 조회

추가 워커/수락 한도 탐색을 중단하고, 필수동의 설정·제출 목록의 PostgreSQL 조회 2회를 1회로 묶었다. 기준은 5adf5d793f116c000238c19d56ef6b87486dd5ae다. 필수동의 진행은 캐시 대신 매번 DB의 동일 statement snapshot에서 읽는다. FilteredRelation으로 JOIN을 현재 사용자에 제한하고, 필수 문서 순서 및 기존 전체 제출 유형 집합을 보존한다. SQLite는 기존 경로를 유지한다.

인증 세대·키 교체·필수동의/보호자 검증·접근 제한·관리자·프론트·URL·모델/migration은 변경하지 않았다. 로그인 시도 식별자를 만드는 코드 GET 세션도 유지했다. 오류 시 인증을 우회하거나 임의로 성공 처리하지 않는다. 개인정보·SQL 원문·세션 값은 로그에 추가하지 않았다.

## 로컬 검증

- 독립 PostgreSQL에서 전체 프로젝트 425개 통과. 새 3개는 결과 동등성/단일 SQL, 설정 즉시 반영과 설정 row 없음, 다른 사용자의 제출 분리를 검증한다.
- 2×8·keep-alive 0·timeout 60·worker_connections 기본값을 유지했다. 연결 한도 30의 일회용 localhost DB이며 Supabase pool 20 자체를 재현하지 않았다.
- 동일 도구로 70ms SQL/BEGIN/commit/healthcheck 지연을 모사했다. 새 DB에서 워밍업 1명+단일 1명+정상 42명을 전후 각각 한 번 실행했다. 실제 지역 간 RTT, 신규 연결 425ms, Render CPU/메모리 제한·프록시 라우팅·브라우저 전체 로딩을 모사하지 않았다. 한 번의 순차 비교로 통계적 유의성을 주장하지 않는다.

## 오늘의 종료 기준

이 후보 외에 새 설정 조합이나 코드 수정은 추가하지 않는다. 원래 운영 저장소의 커밋/푸시·운영 DB 시험·운영 배포는 금지 상태로 유지한다.
스테이징 시험을 수행할 경우 같은 Render 서비스·독립 테스트 DB·풀 20·2×8·동일 fixture/date/hash를 유지하고 이 후보만 교체한다. 정상 42명 2회, 중복 42명 1회로 제한한다. 매회 fixture를 초기화하고 기존 결과를 보존한다.

최종 판정에 필요한 값은 정상 오류/프록시 502/인증 유실/중복 저장 0, 중복 재시도 후 인증 유지, 각 실행의 헬스 전체 응답 및 4초 미만 목표다. duplicate의 원시 409/503과 네트워크 오류는 별도로 보고한다. Events 없음만으로 health timeout 부재를 주장하지 않는다. 프록시 이전/워커 큐 이전 대기도 포함한 클라이언트 응답을 사용한다.
미달하면 같은 시험을 반복해 통과를 찾지 않고 운영 보류로 종료한다. 모든 실측을 통과해도 장시간 부하·실제 풀 대기·장애 이중화 등 미실행 항목은 남은 조건으로 표시한다. 오늘 테스트 종료와 운영 배포 승인은 별개다.

현재 상태: 실제 Render 후보 시험은 미실행, 운영 준비 완료로 판정하지 않음. 로컬 결과/소스 hash는 docs/document-progress-final-20261021/summary.json에 보존했다.
